PureSudoku Code Audit

Summary

  • The code is tidy and the tests pass, but 6 bugs hit what players see most: stats, difficulty, and photo import.
  • Medium and Hard are not harder. Every generated puzzle is "Easy" by the app's own measure, so the levels are almost the same.
  • A player can inflate stats by revealing a solved puzzle again and again. A revealed puzzle also sets a best time.
  • The photo import deletes new photos right away, and probably reads camera photos sideways.
  • About 300 lines and 3.5 MB of unused files can go. No new libraries are needed for any fix.

What this repo does: PureSudoku is an offline iPhone Sudoku app built with SwiftUI. It makes puzzles on the phone, saves games and stats as JSON files, and can import a puzzle from a photo. Load assumed: one person on one phone. The limits that matter are main-thread time (a frozen screen), app size, and saved data staying correct.

Must fix

Wrong results players can see, or lost data
1Revealing a solved puzzle counts the win again▶ Views/GameView.swift:86 · ViewModels/GameViewModel.swift:341
What this is
The game menu has a "Reveal Puzzle" item. It fills in the answer and reports the game as finished.
Problem
The item stays active after the puzzle is solved, and revealPuzzle() does not check isCompleted. Each tap of Reveal → Confirm calls onCompletion again. That adds 1 to "puzzles solved", adds the time again, and can extend the streak.
Fix
Add guard !state.isCompleted else { return } at the top of revealPuzzle(), and .disabled(viewModel.state.isCompleted) on the menu item. Add one unit test: reveal twice, and the completion callback fires once.
If we skip it
Stats can be pushed to any number with a few taps, so they mean nothing.
2Revealed puzzles set best times and streaks▶ Models/Stats.swift:22 · Tests/PureSudokuTests/StatsTests.swift:15
What this is
recordCompletion updates the counts, best time and streak when a game ends.
Problem
It takes a usedReveal flag but never reads it. CODESPEC.md says stats update only for a "puzzle completed without usedReveal". Start a Hard game, reveal it after 3 seconds, and the Hard best time is 3 seconds for good. The test testRevealDoesNotAffectStreakOrBestTime checks the opposite of its own name: it asserts that the reveal did set the streak and best time.
Fix
Start recordCompletion with guard !usedReveal else { return }. Change the test to expect streak 0 and no best time.
If we skip it
Best times can be faked, and the code breaks a clear rule in the spec.
3Medium and Hard are barely harder than Easy▶ Engine/SudokuGeneratorService.swift:11-16, 44-84
What this is
The generator makes a puzzle, then rates it. The rating counts how many guesses the solver needed. A puzzle under 20 counts as Easy, 20–60 as Medium, and 60–120 as Hard. The generator tries up to 25 times to hit the level you asked for.
Problem
I ran the generator 200 times. Ratings ranged from 0 to 5.75 (median 1), so no puzzle ever reached 20. Medium and Hard never match, so both always use all 25 tries and keep the "closest" one. For both levels that is simply the highest of the 25, so Medium and Hard pick puzzles the same way. Every imported puzzle is labelled Easy, and every saved puzzle stores the bucket "easy".
Fix
Set the limits from the real spread, for example Easy < 1, Medium 1–3, Hard ≥ 3. Keep them in one place (see #13). Add a test that makes 30 puzzles per level and checks that the average rating rises from Easy to Hard. For a truly hard level, rate puzzles by the techniques the hint engine needs to solve them. That is a bigger change, so record it in CODESPEC.md first.
If we skip it
The app's main choice, the difficulty level, does almost nothing.
4New import photos are deleted right after saving▶ Persistence/ImportedImageStore.swift:52-58 · ViewModels/AppController.swift:155-173
What this is
When "keep import images" is on, the photo is saved, then cleanup(keeping:) deletes photos that no imported game uses.
Problem
The cleanup runs right after the save, before the new game exists. So the new photo is not on the "keep" list yet. With at least one earlier imported game, the list is not empty, and the new photo is deleted at once. The game later stores an ID that points to a missing file. With zero imported games the list is empty, the code skips deletion, and unused photos pile up to 50.
Fix
Remove cleanupImportImages() from saveImportedImage. Keep the one in persistImportedGames, which runs after the game is created. In cleanup, drop the !ids.isEmpty special case. Also delete the photo when the user taps Discard. Add a test that goes through AppController: import game 1, import game 2, and check that both photos exist.
If we skip it
The "keep images" setting stops working after the first import.
5Camera photos are probably read sideways not tested on a device▶ Engine/SudokuImageDetector.swift:14, 46, 147
What this is
The detector finds the grid and reads each digit with Apple's Vision framework.
Problem
It uses image.cgImage, which drops the photo's rotation flag. An iPhone portrait photo is stored on its side with a "rotate right" flag. Vision then sees the grid turned 90°, and the digits land in the wrong cells (rows become columns).
Fix
Redraw the image upright once at the start of detectGrid (a UIGraphicsImageRenderer draw, about 4 lines). The alternative is to pass the orientation to each VNImageRequestHandler. Check it with one real portrait photo.
If we skip it
The headline import feature fails on the most common kind of photo.
6Imported puzzles with more than one answer can never be finished▶ ViewModels/AppController.swift:113-141 · Engine/SudokuValidator.swift:49 · BYOS.md:10
What this is
Import needs at least 10 digits and a puzzle that can be solved. BYOS.md allows puzzles with more than one answer.
Problem
The app stores one answer, picked at random by the solver, and judges the player against it. With 10–20 digits there are many answers. A player who fills in a different correct grid sees cells marked wrong, and the game never ends.
Fix
The simplest fix is to require one answer at import. checkPuzzle in SudokuGeneratorCore.swift already tests this, so the code only needs to call it, plus a one-line change to BYOS.md. Another option: for imported games, accept any full grid with no repeated digits.
If we skip it
Sparse or misread imports turn into games nobody can win.

Should fix

Slowness, risky code without tests, extra code
7Starting a Medium or Hard game freezes the screen▶ ViewModels/AppController.swift:96 · ViewModels/MainMenuViewModel.swift:36
What this is
Tapping a level makes the puzzle right away, on the main thread. The main thread also draws the screen.
Problem
I measured one try at about 12 ms in an optimized build and 206 ms in a debug build. Because of #3, Medium and Hard always make all 25 tries. That is a ~0.3 s freeze for users and ~5 s while developing. Older phones are slower.
Fix
Fixing #3 removes most of it, because a match then stops the loop early. Also make the puzzle in a background Task and show the grid when it is ready.
If we skip it
The app feels stuck right when a game starts.
8Hints give wrong advice when the board has a mistake▶ ViewModels/GameViewModel.swift:294 · Engine/SudokuHintEngine.swift:35, 764
What this is
Hint looks at the board as the player filled it and suggests the next logical move.
Problem
It catches only repeated digits. A wrong digit with no repeat makes the hint reason from a false board, so it can say "place 5" in a cell whose answer is 7. With auto-fill on, the cell then shows 7, which contradicts the message. "Bowman's Bingo" tries each digit and keeps the one that is not impossible. On a board with a mistake every digit is impossible, so it names a wrong digit.
Fix
Before asking for a hint, compare the player's digits with the answer. If one is wrong, select that cell and say "This cell is not right", which takes about 6 lines. Add a test with one wrong digit.
If we skip it
Players lose trust in hints at the moment they need them most.
9A save file that fails to load is silently replaced▶ ViewModels/AppController.swift:34-64
What this is
At start the app loads settings, stats and games from JSON files. If a load fails it uses empty defaults and sets lastPersistenceError.
Problem
Nothing in the app ever shows lastPersistenceError. The next save writes the defaults over the file. Say a future update adds a stats field but forgets decodeIfPresent: every player's stats load as errors and are wiped on the next save, with no trace.
Fix
When a load fails, rename the file to <name>.corrupt.json before going on, so the data can be recovered. That is about 3 lines in PersistenceManager.load. Then delete lastPersistenceError if nothing will show it. The custom decoders already handle the common case, so this is a safety net.
If we skip it
One coding mistake in a future version can erase player history for good.
10"New Puzzle" does nothing in an imported game▶ ViewModels/AppController.swift:82-93 · Views/GameView.swift:92
What this is
The game menu shows "New Puzzle" in every game.
Problem
makeImportedGameViewModel never sets onNewGame. In an imported game, the player confirms "Start a new puzzle?" and nothing happens.
Fix
Hide the item when state.puzzle.source == .imported.
If we skip it
The app has a button that does nothing.

12About 140 lines of unused code▶ Engine/ · ViewModels/AppController.swift · Models/GameState.swift
What this is
I searched code and tests for each item below, and none is called.
Problem
  • Daily puzzles: GenerationMode.daily, seed(for:), dailyPuzzle and startDailyGame. The seed also uses Swift's Hasher, which changes on every launch, so a "daily" puzzle would differ each time.
  • GeneratorTelemetry: written to disk on every new game, never read (telemetryAverage has no callers).
  • randomPuzzle, fallbackPuzzle, GameState.replace(cell:), and the no-RNG makePuzzle().
  • SudokuValidator.removeCandidates and hasContradiction(in:), which copy code in GameViewModel.
  • The Exocet and Sue de Coq hint steps, which always return false, plus their enum cases.
  • allowVeryHard and veryHardMin, plus a validator.isValid(...) call whose result is thrown away (SudokuPuzzleRepository.swift:62).
Fix
Delete them. Keep .seeded, because a test uses it.
If we skip it
Readers have to work out that this code does nothing, and the daily-puzzle bug waits for whoever turns it on.
13The same small jobs are written 2–4 times▶ GameViewModel.swift · SudokuValidator.swift · SudokuGeneratorService.swift · ImportPuzzleViewModel.swift · AppController.swift
What this is
Code that must change together but lives in several places.
Problem
  • Turning cells or an 81-digit string into the solver's board: 5 copies (GameViewModel.generatorBoard, SudokuValidator.hasContradiction, GeneratorService.hint, solve(initialGrid:), AppController.createImportedGame).
  • Finding repeated digits: 3 copies (ImportPuzzleViewModel.findConflicts, SudokuValidator.conflictingIndices, hasContradiction).
  • The difficulty limits: 2 copies (difficulty(for:) and bucket(for:)). This is why #3 must be fixed in two places.
  • "Cells in the same row, column or box": 3 ways (removeCandidate, computeCandidateOverlay, peerMap).
Fix
Add one small Engine/Board.swift with board(from cells:), board(from grid:) and a fixed peers table. Have ImportPuzzleViewModel use hasContradiction, and make difficulty(for:) call bucket(for:). That saves about 60 lines.
If we skip it
A rule fixed in one copy stays wrong in the others, as #3 already shows.
14The hint steps are 13 copy-pasted blocks▶ Engine/SudokuHintEngine.swift:48-189
What this is
nextHint tries each solving technique in order.
Problem
Each technique is a 10-line block that differs only in its name and function. That is 140 lines for one loop, and adding a technique means copying a block again.
Fix
Make a list of (technique, apply) pairs and loop over it with hintAfterElimination. That takes about 25 lines, and the order stays visible in one place.
If we skip it
About 115 extra lines to read, and a risk that a pasted block gets the wrong name.
15No tests cover findings 1–4▶ Tests/PureSudokuTests/
What this is
There are 27 unit tests, and all pass.
Problem
No test fails if a win is counted twice, a reveal sets a best time, the levels match, or a new photo is deleted. One stats test even locks in the wrong behavior (#2). ImportedImageStoreTests calls the store directly, so it never runs the AppController order that causes #4.
Fix
Add the single test named in each of #1–#4. No new test tools are needed.
If we skip it
The same bugs can come back unnoticed after they are fixed.

Nice to have

Small speed-ups and shorter code
16The timer redraws the whole grid every second▶ ViewModels/GameViewModel.swift:550-560
What this is
Each second, tick() adds 1 to elapsedSeconds, which lives inside the published state.
Problem
Every tick changes state, so SwiftUI checks all 81 cells again. With "Show Candidates" on, it also rebuilds the candidate overlay, about 20,000 cell checks, even though no cell changed.
Fix
Remove refreshCandidateOverlayIfNeeded() from tick(), a one-line change. Optionally publish the elapsed time apart from state.
If we skip it
The phone does a little extra work every second, which costs some battery in long games.
17Settings and stats saves are delayed for no reason▶ ViewModels/AppController.swift:143-184
What this is
updateSettings and updateStats wrap their work in DispatchQueue.main.async.
Problem
The class already runs on the main thread (@MainActor), so the wrapper only delays the change. Code that reads settings right after calling updateSettings sees the old value.
Fix
Remove the wrapper and run the block directly. That is 4 lines shorter.
If we skip it
The delay can cause bugs that are hard to explain.
18The answer is re-split on every check▶ Engine/SudokuValidator.swift:36-57
What this is
isCorrect and solutionValue look up one cell in the answer string.
Problem
Each call turns the whole 81-character string into an array. isSolved calls it up to 81 times per move, which builds 81 arrays.
Fix
Turn the answer into [Int] once in isSolved, or store it that way on SudokuPuzzle.
If we skip it
Nobody will notice the cost today.

Verdict: Fix 1–4 first. Each takes a few lines, and they decide whether the stats, levels and photo import are right. Then fix 5 and 6 and check them on a device.

Lean: about −300 lines (unused code 140, hint loop 115, shared board helper 60) and −3.5 MB of app size possible. No dependencies to remove; the app has none.

Not checked: I did not check whether the advanced hint techniques (XY-Chain, Medusa, Unique Rectangle, Swordfish) are correct. I did not run the photo import on a real device, and did not time the 81 separate Vision digit reads. I only skimmed the Settings, Stats, Theme, NumberPad and Import screens. I measured generation in a Mac command-line build, not on a phone.
